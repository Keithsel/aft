# v0.49 unified tool surface

This repository copy is the S0 specification spine. The checked inventory and
stable cross-section identifiers live in
[`v0.49-unified-tool-surface-inventory.json`](./v0.49-unified-tool-surface-inventory.json).
S0 records the contract and inventories only; it does not implement runtime
normalization, registration, installer, or mutation changes.

The accepted addenda below are retained as normative text. Later slices must
reference their stable IDs and must not silently narrow, reorder, or reinterpret
their requirements.

## intent

Resolve GitHub issue #165 by publishing one canonical agent-facing file vocabulary and one edit contract on OpenCode and Pi in v0.49. All schema and steering-text changes ship together so the release causes one intentional prefix-cache invalidation.

1. **Canonical file-path vocabulary.** Any agent-facing property whose semantic role is a single source or subject file path and whose legacy name is `filePath` becomes `path`, including occurrences nested inside arrays or objects such as `aft_zoom.targets[].path`. `aft_callgraph.toFile` becomes `toPath`. Runtime compatibility accepts the retired spellings before validation, but emitted schemas, descriptions, examples, prompts, and current documentation contain only canonical spellings.
2. **Public edit modes.** The public `edit` schema exposes `path` and exactly three mutually exclusive modes: append via `appendContent`, batch editing via non-empty `edits[]`, and symbol replacement via `symbol` plus `content`. "edits[]-only" means that public find/replace inputs exist only as items in `edits[]`; top-level `oldString`, `newString`, `replaceAll`, and `occurrence` are absent from the schema. A pre-validation compatibility shim folds a valid legacy top-level find/replace request into one `edits[]` item.
3. **One-based occurrence selection.** Every public and compatibility find/replace item interprets `occurrence: 1` as the first match and `occurrence: 2` as the second. Rust implements this directly; TypeScript does not translate indices. `occurrence: 0` is intentionally invalid and is not treated as an omitted value.

The retained append and symbol modes are justified by observed production success rates. The compatibility shims are required because the legacy top-level find/replace form remains common in production. Acceptance targets the measured failure signatures represented by the regression cases below; it does not claim that every edit failure in the broader measured categories is eliminated.

## constraints

- All canonical schema and description changes land in v0.49; no transition configuration or dual-schema publication is provided.
- The `filePath` and `toFile` aliases, the legacy top-level find/replace fold, JSON-stringified `edits`, and `oldText`/`newText` item aliases are silent compatibility behavior retained until a future specification explicitly removes them. v0.49 emits no deprecation warnings.
- Compatibility preprocessing must run before schema validation on Pi and OpenCode and before manifest-schema validation in subc translation.
- Rust is the source of truth for one-based occurrence semantics; no TypeScript off-by-one adapter is permitted.
- No root-level `anyOf`, `oneOf`, or `allOf` is introduced.
- `crates/aft/src/subc_tool_schemas.json` is regenerated only by the final integration slice using `bun scripts/build-tool-schemas.ts`; the byte-drift guard runs in that slice.
- Translate fixtures are edited or added individually. Bulk regeneration of frozen golden fixtures is prohibited.
- The canonical surface and compatibility behavior apply equally to trusted and untrusted/MCP binds.
- The upstream OpenCode change that renders `input.path ?? input.filePath` is a v0.49 ship prerequisite. The release check must exercise a path-only edit and write in both TUI and Desktop/web and confirm title, directory, and diff display. The release does not accept a known path-only display degradation.
- `aft_move` keeps `destination`; `apply_patch` keeps `patchText`; collection and polymorphic path roles such as `files` and `target` retain their names.
- Steering-text vocabulary checks cover schemas, descriptions, examples, error strings, prompt snippets, prompt guidelines, plugin READMEs, and `docs/`. Remaining legacy vocabulary must appear in an explicit allowlist with file, location, and reason.

## interfaces

### Canonical path-property rule

Maintain the checked inventory `INV-V049-CANONICAL-PATH-001` in the companion manifest. It is checked against every registered OpenCode tool, every registered Pi tool, and `crates/aft/src/subc_tool_schemas.json`. For every canonical path property, the inventory records the harness or artifact, tool name, JSON Pointer template, semantic role, canonical spelling, accepted legacy spelling, baseline spelling, and requiredness rule. Apply these rules at every nesting depth:

- Rename a single subject/source file property named `filePath` to `path`.
- Rename `aft_callgraph.toFile` to `toPath`.
- Rename nested subject-file properties, including `aft_zoom.targets[].filePath`, to `path`.
- Keep role-specific properties whose meanings are not the single subject/source file: `destination`, `target`, `files`, `url`, and `patchText`.
- Preserve the legacy property's requiredness unless this specification explicitly changes it.
- Internal variables, Rust command fields, protocol payload fields, compatibility code, compatibility fixtures, and marked historical notes may retain legacy names only when listed in the legacy-vocabulary allowlist with file, location, and reason.

The following requiredness rules are normative:

- OpenCode and Pi `read.path`, `write.path`, and `edit.path` are schema-required.
- `aft_callgraph.path` is required and `aft_callgraph.toPath` is optional.
- `aft_move.path` and `aft_move.destination` are required.
- Every `aft_zoom.targets[]` item requires `path` and `symbol`.
- Properties that are optional at the root because their necessity depends on an operation, including `aft_safety.path`, remain optional in the schema and retain their operation-specific runtime requirement.
- Collection and polymorphic roles retained under names such as `files` and `target` keep their existing requiredness.

The schema audit compares every emitted schema against the inventory and fails on a missing property, unexpected property, wrong spelling, wrong nesting location, or requiredness mismatch.

For each canonical/legacy pair, preprocessing follows the same rule in both harnesses and subc translation:

- canonical only: use the canonical value;
- legacy only: copy it to the canonical property and remove the legacy property before validation;
- both with equal string values: retain the canonical property and remove the legacy property;
- both with unequal values or incompatible types: return `invalid_request` naming both properties and perform no mutation.

This rule applies to `path`/`filePath`, nested `path`/`filePath`, and `toPath`/`toFile`. Compatibility applies to trusted and untrusted subc binds. Legacy names never appear in emitted schemas.

The complete row-level contract, including retained collection and polymorphic roles, is `INV-V049-CANONICAL-PATH-001`.

### Shared-surface parity

Maintain the checked shared-tool inventory `INV-V049-SHARED-TOOLS-001` rather than deriving parity from the intersection of the two harnesses at test time. The inventory identifies every tool expected on both OpenCode and Pi. Any intentionally host-only registration must appear in the separate checked allowlist `LIST-V049-HOST-ONLY-TOOLS-001`, containing the harness, tool name, reason, and owning test.

After removing only allowlisted host-only registrations, assert that the OpenCode and Pi registered-tool name sets are exactly equal to each other and exactly equal to the checked shared-tool inventory. A missing or extra unallowlisted tool is a parity failure.

For every inventoried shared tool, compare a canonical projection consisting of:

1. registered tool name;
2. recursively key-sorted JSON Schema;
3. agent-visible description; and
4. contract-owned error code and message for shared validation fixtures.

The serialized canonical projections must be byte-identical. Host wrappers, rendering callbacks, metadata, and host-only registration fields are excluded. Prompt snippets and prompt guidelines have a separate vocabulary audit because OpenCode does not expose matching host fields.

### Checked subc capability inventory

`INV-V049-SUBC-CAPABILITY-001` identifies the 21 bare manifest names, the generated-schema owner, the Rust loading point, trusted and untrusted translation stages, and the preview capability status for each command. A `not a mutation` entry is a checked classification; an `unknown` entry is an explicit unresolved capability and is not permission to assume preview support.

### Registration profiles

`MAN-V049-REGISTRATION-PROFILES-001` records OpenCode and Pi minimal, recommended, and all profiles, feature predicates, canonical host names, and host-only branches. `REG-V049-OC-ALL` and `REG-V049-PI-ALL` are the full shared parity profiles. Surface flags, disabled tools, backup settings, bash background settings, search-index settings, semantic-search settings, and inspect settings remain predicates rather than facts about every production process.

## alias compatibility

The canonical path alias pairs are `path`/`filePath`, including nested subject-file properties, and `toPath`/`toFile` for `aft_callgraph`. For these pairs, canonical-only and legacy-only inputs normalize to the canonical property; equal dual values succeed; unequal values or incompatible types return `invalid_request` naming both properties with zero mutation. These rules apply equally to OpenCode, Pi, trusted subc, and untrusted subc.

The edit-item compatibility pairs `oldString`/`oldText` and `newString`/`newText` intentionally use a different conflict policy: canonical item spellings win whenever both are present, and the legacy properties are removed before validation. These aliases are accepted only inside edit items and never appear in emitted schemas.

Top-level `oldString`, `newString`, `replaceAll`, and `occurrence` are compatibility fields for the hidden single-edit fold, not aliases for public top-level schema properties. Their presence participates in mode-conflict detection as defined by the edit normalization pipeline.

## compatibility boundary

For every registered OpenCode and Pi tool, raw model arguments pass through a tool-registration preparation adapter before the canonical emitted schema is applied. Trusted and untrusted subc requests pass through the equivalent translation preparation stage before manifest-schema validation. These stages receive the unmodified raw argument object, perform only the compatibility normalization defined by this specification, and pass a canonical-only object to the ordinary validator and handler.

A tool execute handler that receives arguments only after host validation is not, by itself, a valid implementation location for compatibility preprocessing. Implementations must not depend on schema-unknown legacy properties surviving host parsing or unknown-property stripping. If a host does not expose a native preparation hook, the plugin registration bridge must interpose an equivalent raw-argument stage while continuing to report the strict canonical schema to agents and host schema inspectors.

Legacy properties remain absent from emitted schemas. Compatibility must not be implemented by adding hidden, optional, permissive, or undocumented legacy properties to the reported schema. Boundary tests must submit legacy-only calls through the actual host invocation API and prove that preparation saw and normalized the legacy properties before canonical validation.

## edit normalization and validation

Every OpenCode, Pi, trusted-subc, and untrusted-subc edit request follows this pipeline on the raw argument object before emitted-schema validation. Compatibility-only properties must remain observable to this pipeline even though they are absent from emitted schemas.

1. Normalize `path`/`filePath` using the canonical path-alias rule.
2. Detect own-property presence of top-level `startLine` or `endLine`. Either property at the edit root returns `invalid_request` with a contract-owned message stating that line-range fields are valid only inside `edits[]` and showing the canonical shape `edits: [{ startLine, endLine, content }]`. The message names every supplied top-level line-range field. This rejection occurs before edit-mode counting or unknown-property stripping, including when the fields are mixed with a canonical edit mode.
3. Determine mode presence from own-property presence before parsing or coercing mode payloads. Append mode is present when `appendContent` is present; edits mode when `edits` is present; symbol mode when either `symbol` or `content` is present; hidden single-edit mode when any top-level `oldString`, `newString`, `replaceAll`, or `occurrence` is present.
4. If more than one mode is present, return `invalid_request` naming the conflicting mode fields. This check occurs before parsing stringified `edits`, so `appendContent` combined with malformed stringified `edits` is a mode-conflict error rather than append success or an edits-JSON error.
5. If no mode is present, return `invalid_request` stating that exactly one of `appendContent`, `edits`, or `symbol` plus `content` is required.
6. If edits mode is selected and `edits` is a string, parse it as JSON. Parse failure or a parsed root other than an array returns `invalid_request`.
7. If hidden single-edit mode is selected, validate the top-level fields as one find/replace item and then move them into a one-item `edits` array. `oldString` is required and must be a string. Optional `newString`, `replaceAll`, and `occurrence` retain identical semantics after folding. Remove the hidden top-level properties before canonical schema validation.
8. Within each edit item, normalize `oldText` to `oldString` and `newText` to `newString`. If both legacy and canonical spellings are present, the canonical value wins even when the values differ. The winning canonical value must still satisfy canonical type validation. Remove the legacy properties before validation.
9. Apply compatibility scalar coercion using the explicit accepted domains in `INV-V049-COMPATIBILITY-SCALARS-001`.
10. Validate the complete canonical request and every edit item before permission requests, formatter invocation, backup creation, diff generation, or file mutation.

For `replaceAll`, accept booleans directly; accept every ASCII casing permutation of the strings `"true"` and `"false"`; and accept numeric or string values `1` and `0` as true and false respectively. Any other explicitly supplied value, including null, arrays, objects, non-integral numbers, numbers other than 0 and 1, and unrelated strings, returns `invalid_request`. Missing `replaceAll` remains absent.

For `occurrence`, accept positive integer numeric values within the JavaScript safe-integer range. A string is an integral numeric string only after trimming ASCII whitespace and only when the trimmed value matches `^[+]?[0-9]+$`. Leading zeros and a single leading plus sign are accepted. Decimal points, exponent notation, negative signs, hexadecimal or other radix prefixes, `NaN`, and infinity spellings are rejected. The parsed mathematical value must not exceed `Number.MAX_SAFE_INTEGER`.

For `occurrence`, explicit null, the empty string, and an ASCII-whitespace-only string are omission sentinels. Numeric zero and every accepted lexical spelling of zero, including `"0"`, `"00"`, and `"+0"`, are not omission sentinels and return `invalid_request`. Negative values, overflow values, non-integral numbers, arrays, objects, and strings outside the accepted grammar also return `invalid_request`. These grammar, bounds, and omission rules apply identically to canonical edit items and the hidden top-level fold on every compatibility boundary.

The canonical public edit schema requires `path` and exposes optional `appendContent`, optional non-empty `edits`, optional `symbol`, and optional `content`. It does not expose top-level `oldString`, `newString`, `replaceAll`, `occurrence`, `oldText`, `newText`, `startLine`, or `endLine`. Because root-level combinators are prohibited, mode exclusivity and the requirement to select one mode are enforced by the preprocessing and runtime validation pipeline.

Exactly one canonical edit mode must resolve:

- Append: `appendContent` is a string, including the empty string.
- Batch: `edits` is an array with `minItems: 1`.
- Symbol replacement: both `symbol` and `content` are strings. Supplying only one returns `invalid_request` naming the missing partner.

Each `edits[i]` must be an object resolving to exactly one of these shapes:

- Find/replace: required string `oldString`; optional string `newString`; optional boolean `replaceAll`; optional integer `occurrence` with minimum 1 and maximum `Number.MAX_SAFE_INTEGER`. `replaceAll` and `occurrence` are mutually exclusive when both properties are present, regardless of the boolean value of `replaceAll`.
- Line range: required integer `startLine`, required integer `endLine`, and required string `content`. Lines are 1-based and inclusive, and `startLine <= endLine`.

Empty, non-object, mixed-shape, wrong-typed, or unknown-property items return `invalid_request` naming `edits[i]`. Validation is atomic. For an execution request, failure occurs before any preview generation, permission request, formatter invocation, backup creation, or mutation. For an explicit preview request, normalization and validation run and return the same contract failure, but no downstream diff generation or mutation occurs after validation fails. Every successful preview leaves the file and all mutation-related state unchanged.

The hidden fold is independently identified as `FOLD-V049-HIDDEN-SINGLE-EDIT-001`; the complete shared error and mutation fixture table is `TBL-V049-CONTRACT-FIXTURES-001`.

## error contract

Contract validation failures use the logical code `invalid_request`. Rust/subc returns that code in its structured failure response. Each plugin must preserve the code in the host-supported tool-error metadata or structured cause even if the host also renders or wraps the human-readable message. Tests assert the logical code before comparing messages and do not compare incidental host prefixes, stack traces, or transport wrappers.

The contract-owned error corpus consists of the shared fixtures for path-alias conflict, toPath-alias conflict, edit-mode conflict, no edit mode, top-level line-range rejection, malformed stringified edits, non-array parsed edits, missing symbol/content partner, empty edits, invalid `edits[i]`, replaceAll/occurrence conflict, occurrence below 1, occurrence overflow, invalid occurrence string grammar, and ambiguous match guidance. Top-level line-range fixtures cover `startLine` alone, `endLine` alone, both fields with `content`, and line-range fields mixed with each canonical edit mode.

For these fixtures, the logical code and normalized contract message are byte-identical across OpenCode and Pi. Normalization may remove only documented host wrapping; it may not rewrite field names, indices, canonical-shape guidance, or indexing guidance.

## design

The release uses one canonical schema surface backed by a pre-validation compatibility layer.

1. A checked inventory classifies every registered path-bearing property and drives emitted-schema assertions for OpenCode, Pi, and the generated Rust schema artifact.
2. Each host installs normalization at its raw registration boundary. Normalization applies canonical-over-legacy precedence, converts supported legacy aliases, classifies edit mode by property presence, parses stringified `edits` only when edits mode is selected, and removes compatibility-only properties.
3. The normalized object proceeds through canonical schema validation and then through shared runtime validation for conditions that cannot be represented without prohibited root combinators.
4. Runtime edit validation accepts exactly one item shape per `edits[]` element, enforces 1-based occurrence semantics, and rejects malformed or mixed items before file mutation.
5. TypeScript validates and forwards occurrence selectors without index conversion. Rust validates signed values before conversion and selects the internal match at `occurrence - 1`.
6. Shared snapshots, translated-request fixtures, schema drift checks, host integration tests, UI checks, and the weak-model battery establish parity through the released host paths.

The checked inventories are evidence ledgers, not runtime implementations. Later slices own the adapters, schema regeneration, translation changes, and mutation tests fenced out of S0.

## glossary

- **Canonical field:** The agent-visible property name published in schemas, descriptions, examples, prompts, and documentation.
- **Legacy alias:** A schema-hidden, input-only property accepted for compatibility and removed during normalization.
- **Raw-argument normalization:** Processing performed on the original tool argument object before host schema validation, unknown-property stripping, required-field rejection, or execute-handler type narrowing.
- **Shared tool surface:** Tool names, descriptions, requiredness, properties, types, bounds, and item schemas exposed by both OpenCode and Pi.
- **Hidden single-edit mode:** Compatibility handling that folds top-level `oldString`, `newString`, `replaceAll`, and `occurrence` into one `edits[]` item.
- **Explicit edits mode:** Edit mode selected by the presence of the visible `edits` property, including a stringified JSON array accepted by compatibility normalization.
- **Occurrence:** A 1-based selector identifying one match among N matches.
- **Path-bearing property:** A property whose value identifies a local source file, destination, file collection, URL, or patch payload and therefore must be classified by the checked inventory.
- **Real registered host entry point:** The OpenCode or Pi registration path through which a tool call passes in production; direct calls to a normalizer or execute handler are not equivalent evidence.
- **Checked inventory:** A versioned, stable-ID manifest that enumerates the contract rows and the source artifacts against which later schema and parity checks run.
- **Registration profile:** A host/surface/feature predicate set that determines which tools are registered; it is distinct from the full shared parity projection.
- **Capability status:** One of checked, contractual, target, or unknown; unknown means the repository does not establish the capability and later evidence is required.

## acceptance criteria

### Surface and vocabulary

- Build the registered-tool inventory for both harnesses and the subc artifact, then assert the canonical path-property rule recursively at every schema depth.
- Assert that `filePath` and `toFile` occur zero times in emitted schemas, including nested `aft_zoom.targets[]` items.
- Assert that `aft_callgraph` exposes `path` and optional `toPath`, while `aft_move` exposes `path` and `destination`.
- Assert that both harnesses expose the same edit properties: required `path`, optional `appendContent`, optional non-empty `edits`, optional `symbol`, and optional `content`; neither exposes top-level find/replace properties.
- Compare the recursively canonicalized shared-surface projections and require byte equality.
- Run the steering-text audit and require every retained legacy occurrence to match the checked allowlist.

### Alias compatibility

For OpenCode, Pi, trusted subc, and untrusted subc, test canonical-only, legacy-only, equal dual-spelling, and unequal dual-spelling requests for each applicable alias pair. Canonical and legacy-only requests must produce equivalent results. Equal dual spelling must succeed. Unequal dual spelling must return `invalid_request` naming both fields with zero mutation.

### Edit modes and validation

Run each mutation case through preview where supported and through real execution:

1. append-only succeeds;
2. non-empty `edits[]` find/replace succeeds;
3. symbol plus content succeeds on both harnesses;
4. legacy top-level `oldString`/`newString` produces the same result as one canonical edit item;
5. hidden `replaceAll` and `occurrence` survive folding with unchanged one-based semantics;
6. valid JSON-stringified `edits` succeeds;
7. malformed JSON and JSON whose root is not an array return `invalid_request` with zero mutation;
8. each pair of modes returns `invalid_request` naming the conflicting fields with zero mutation;
9. symbol without content and content without symbol fail with zero mutation;
10. empty arrays and invalid batch items fail naming `edits[i]` with zero mutation;
11. `replaceAll` plus `occurrence` fails with zero mutation;
12. line-range `{startLine, endLine, content}` remains 1-based, inclusive, and atomic;
13. `oldText`/`newText` item aliases normalize successfully, and canonical item spellings win when both are supplied.

### Occurrence regression flip

- On a file with one match, `occurrence: 1` succeeds.
- On a file with at least two matches, `occurrence: 2` selects the second.
- `occurrence: 0` returns `invalid_request` and leaves the file unchanged.
- An ambiguous request returns guidance containing `occurrence` and `1-based` and containing neither `0-based` nor `0-indexed`.

### Integration and release gates

- Pi and OpenCode plugin suites pass.
- Rust workspace nextest, including the serialized watcher suite, passes.
- Subc parity, hand-maintained translation fixtures, cross-language configuration parity, schema drift guard, and 3-OS CI pass.
- TUI and Desktop/web display checks pass for path-only edit and write calls after the upstream OpenCode compatibility change is available.
- Issue #165 is closed with the canonical shape, compatibility behavior, one-based migration, and reporter credit documented.

### Weak-model evidence

Record a reproducible real-binary session battery using a named model and immutable model/version identifier. The artifact records the prompts, model settings, raw tool calls, normalized calls, outputs, and commit. It includes at least one successful attempt for each of: legacy `filePath`, legacy top-level find/replace, JSON-stringified `edits`, and `occurrence: 1` on one match. A schema-shape failure means host rejection, missing required canonical data after preprocessing, or an unexpected mode-resolution error. The recorded gate requires zero such failures in the declared battery.

## open_assumptions

- The OpenCode and Pi registration systems continue to provide a raw-argument lifecycle point before schema validation and unknown-property stripping. The real-entry-point tests must fail if this ordering is unavailable or changes.
- Existing empty-append behavior, empty replacement defaults, boolean/integer compatibility coercions, and established edit-failure codes remain available unless a criterion in this specification explicitly overrides them.
- The checked inventory is the authoritative enumeration mechanism for registered path-bearing fields; discovering an unclassified field expands the inventory and implementation work rather than creating an implicit exception.
- Historical notes, compatibility tests, and internal identifiers may retain legacy vocabulary only when explicitly recorded by the audit allowlist.
- There are no unresolved product-level questions for the v0.49 surface contract.

The following host and release capabilities remain unresolved and are deliberately recorded as assumptions rather than repository facts:

- **OA-V049-001 — raw host preparation:** The source shows registration and execute handlers, but does not by itself prove a raw-argument hook before host schema validation and unknown-property stripping. Later boundary tests must prove this for OpenCode and Pi.
- **OA-V049-002 — production cache-key observability:** The repository does not expose production prefix-cache keys or telemetry proving the intended one-time invalidation. The release must measure this externally or report the gap; S0 makes no production observability claim.
